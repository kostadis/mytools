# Rust PDF Worker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Replace v2's PDF reader with a streamed standalone Rust command while preserving historical cached work.

**Architecture:** `pdf-reader/` owns the CLI and patched PDF dependencies; a Python process adapter validates its protocol and caches page facts. v2 consumes this adapter; legacy PDF utilities load compatibility dependencies only when used. Rust extracts and response bindings are versioned separately.

**Tech Stack:** Rust/lopdf 0.47/pdf-extract, JSON Lines, Python standard library, pytest.

**Spec:** `docs/superpowers/specs/2026-11-24-rust-pdf-worker-design.md`

## Global Constraints

- Rust and a standalone worker are approved; accept size-related memory growth.
- Stdout protocol version 1; page numbers 1-based; invalid selections exit 2, failures exit 1.
- Missing/truncated/partial protocol output must not publish a successful extraction.
- No eager PyMuPDF import or worker on Markdown-only paths; no silent PDF-engine fallback.
- Retain all source PDFs and historical caches; bind new response reuse to exact prompts/settings.
- Offline acceptance only, at most five pages per private comparison PDF; no service restart or library reconversion.

## Review Focus

- Empty-password encryption, indirect references and compressed object streams must survive raw-object lifetime changes.
- Containers without destinations and duplicate bookmark titles preserve order and real page mappings.
- Form XObjects carry text; bitmap images do not become PDF instructions; spacing preserves words/numbers.
- Child-process protocol failure, stderr saturation and cancellation cannot leave partial success or orphan children.
- Backend/prompt changes cannot select historical ordinal/title-only responses or overwrite legacy extract artifacts.
