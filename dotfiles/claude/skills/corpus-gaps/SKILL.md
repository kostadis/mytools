description: >
  Find campaign files that belong in the mneme declared corpus (.mneme/corpus.yaml)
  but are not in it, and walk them with the GM. A deterministic scanner lists every
  readable file that is neither declared nor already ruled out, ranked: files added
  since corpus.yaml was last committed, new siblings of a `files:` list (which never
  picks up a new file by itself), then the older backlog. The GM rules each one: add
  to a kind, add a new kind (GM states its trust), rule out, or defer. Adds are
  written to corpus.yaml, outs to .mneme/corpus.rulings.yaml so they never re-surface,
  then check, render, refresh, status, backup. Use when the user asks what is missing
  from the corpus/mempalace, after adding a new kind of document (arcs, strategy docs,
  handouts), or when `mneme mp status` is clean but a new file is not searchable.
  Invoke as /corpus-gaps [campaign-dir].
tools: Read, Edit, Write, Bash, AskUserQuestion, Artifact

# corpus-gaps

A declared-corpus campaign mines **only** what `.mneme/corpus.yaml` names. That is the
point of the corpus, and it is also how files go missing quietly. A new document type
gets its own directory (`docs/arcs/`, say), or a new file lands next to a kind that
lists its files one by one. Nothing is mined and nothing complains: `mneme mp status`
compares the palace with the *declaration*, so it stays green.

This skill is the check that runs in the other direction: from the disk to the
declaration.

## What is a decision, and whose

The scanner decides nothing. **Membership, kind and trust are precision decisions,
and they are the GM's.** Trust matters most: an `authoritative` kind becomes a
`canon_wing`, and CampaignGenerator's grounded search verifies claims against it. So a
file of hopes, plans or overlays in an authoritative kind gets cited as canon. Never
pick trust yourself. When you recommend, say why.

## Files

| File | Owner | Role |
|---|---|---|
| `.mneme/corpus.yaml` | GM (origin) | What is mined. `mneme corpus check` validates it. It rejects unknown top-level keys, so out-rulings cannot live here. |
| `.mneme/corpus.rulings.yaml` | GM (origin) | What the GM ruled **out**, so the scan never re-asks. mneme does not read it. |
| `.mneme/corpus.toc.json`, root `mempalace.yaml`, the `mempalace:` block of `config/config.yaml` | mneme (replicas) | Regenerated by `mneme mp render`. Never hand-edit them, and never read the TOC snapshot as the corpus. |
| `scan_gaps.py` (next to this file) | skill | Read-only scanner. |

Rulings file format:

```yaml
campaign: <name>
excluded:
  - path: docs/some_pipeline_dir/   # trailing "/" = the whole subtree
    ruled: 2026-01-31
    reason: pipeline
  - path: notes/one_file.md         # no slash = exactly this file
    ruled: 2026-01-31
    reason: superseded by docs/x.md
```

If the campaign has no rulings file yet, offer to create one on the first out-ruling.
If the campaign's corpus was built from a recorded decision worksheet, seed the file
from that worksheet's explicit "left out" list. Use only the GM's recorded words; do
not infer outs.

## Steps

### 1. Preconditions

- You are inside a campaign directory that has `.mneme/corpus.yaml`. If it has no
  corpus, stop. This skill does not do a wing-model campaign or a first declaration.
- `mneme corpus check <campaign> --dir <campaign-dir>` reports valid. **Always pass
  `--dir`.** Name lookup fails on hosts whose `data_roots` do not list the campaign,
  and on foreign-owned copies.
- Note `git status`. Untracked files are scanned too, and flagged.
- **Know what a `dirs:` entry already covers.** If the GM's question is "is my new
  work in the corpus?", check first: a new file under a directory a kind lists in
  `dirs:` (e.g. `notes/session_prep/`, `notes/statblocks/`) is already declared, and
  is mined on the next `mp refresh` with no ruling. Say so, and only ask about what
  the scanner actually reports. Images and other non-readable files are never mined.

### 2. Scan

Run the scanner with mneme's own interpreter. The readable-extension list and the
recipe's baseline exclusions are imported from mneme, never copied:

```bash
PY="$(head -1 "$(command -v mneme)" | sed 's/^#!//')"
"$PY" ~/.claude/skills/corpus-gaps/scan_gaps.py <campaign-dir>          # text report
"$PY" ~/.claude/skills/corpus-gaps/scan_gaps.py <campaign-dir> --json   # for building a review page
```

Options: `--since REV` (count files added after REV as new; the default is the last
commit to corpus.yaml), `--all-ext` (every readable extension, not only `.md`/`.txt`),
`--depth N` / `--collapse N` (how large new or backlog subtrees fold into one row).

The report has three signals, strongest first:

| Signal | Meaning | Usual ruling |
|---|---|---|
| `new` | Added (or renamed into place) after corpus.yaml was last committed, or untracked | Most real gaps are here: a new document type, or a new file a `files:` list missed |
| `sibling` | In a directory where a kind lists files one by one; `-> kinds` names them | Add it to that kind's `files:`, or rule it out |
| `backlog` | Older, never ruled on; big subtrees folded into one `dir/ [N files]` row | Usually pipeline output. Rule out the whole subtree in one ruling. |

The scanner also prints **STALE** rulings (the path no longer exists) and
**CONFLICT**s (a path is both declared and ruled out). Bring both to the GM. Do not
delete or resolve them yourself.

**History.** Over the same window (since `corpus.yaml` was last committed, or
`--since`), the scanner reads git history for what the disk-side scan cannot see. A
rename counts as an addition of its new path.

- **New files under out-rulings**, grouped by ruling plus two path levels. A subtree
  ruling silently swallows every file that lands there, including a new kind of
  document. Read the families and check that each still fits its ruling's reason.
  Show the GM the table in one line per family. Bring any family that doesn't fit
  as its own question. Never quietly accept it, and never edit the ruling yourself.
- **Declared files deleted or renamed away**, with where a rename went and that
  path's status now (declared, candidate, ruled out). Their drawers can still sit
  in the palace, so expect `UNDECLARED-DRAWERS` after the refresh (step 5.4). A
  rename whose new path is a candidate is a ruling to bring like any other.

*Why (obelisk, 2026-11-01): the GM asked that the scan look at recent git history.
The first run showed 198 recent arrivals under subtree rulings that the disk scan
never mentioned.*

The last line, `N other minable file(s) not shown`, counts files in other formats
(JSON, YAML, PDF). They are not mined unless declared. Mention the count; don't put
them in front of the GM unless one is plainly a document.

**A folded row hides its contents.** `docs/background/ [11 files]` can hold real
reference material next to the pipeline output that triggered the fold. Before you
describe any folded row to the GM as one thing, expand it and look:

```bash
"$PY" ~/.claude/skills/corpus-gaps/scan_gaps.py <campaign-dir> --collapse 100000 --depth 9 --json
```

*Failure this fixes (toee, 2026-11-01): `docs/background/` was presented inside a
bulk "pipeline output" row. Expanding it after the GM approved that row turned up
three module proper-noun inventories, which the GM then chose to add. They were
nearly ruled out without the GM ever seeing them.*

### 3. Prepare each ruling

For every candidate (or folded subtree), give the GM:

- the path, its signal, and whether it is untracked;
- one line on what the file *is* (read its head). Name the tool that generated it,
  if it has a generated header;
- whether it is a **replica** of something already declared (byte-identical, or a
  generated copy). A replica is normally ruled out, with its origin named;
- the options: **add to `<kind>`** (the scanner's suggested kinds first), **new kind**
  (the GM gives the name and the trust), **rule out** (with a short reason), **defer**
  (nothing is written; it comes back next scan);
- your recommendation and why, including the trust consequence for any add.

Group related files into one ruling where the GM would rule them together (a whole
new directory, a family of strategy docs). Never split a ruling just to make the
queue look longer, and never merge unrelated files to make it shorter.

#### A large backlog: triage into families, not cards

A first run on an established campaign can report thousands of files (toee: about
5,900). **No GM can review that, and a 6,000-card page is not a checkpoint.** Do the
sorting yourself, then put a short list of decisions in front of the GM:

1. **Group every candidate into families** by path (strip the per-session directory
   from `summaries/<session>/…` so all sessions' `staged_review/` become one family).
   Count each family and read one example's head.
2. **Separate the judgment calls from the pipeline.** A judgment call is a family a
   GM might plausibly want searchable: source material (supplement text, module
   inventories), canon-adjacent records (the spelling glossary, staged names), old
   narrative documents (a bible, chapter splits), a wiki. Pipeline is everything a
   tool wrote for another tool: extractions, staged-review manifests, narration
   passes, per-run state, batch scratch, LLM response files, drafts, generated
   projections, empty stubs.
3. **Present one table**, one row per judgment call plus **one bulk row for all
   pipeline output**, each with what it is and your recommendation. In toee this was
   six rows for 5,900 files.
4. **The bulk row lists every subtree it covers, by path.** The GM's approval covers
   exactly that list. Anything you find afterwards that is not on it (see "A folded
   row hides its contents") goes back to the GM as its own question. It is never
   swept in.
5. **Look for replicas before calling something canon.** A family that is the
   origin or a copy of a declared kind (e.g. `summaries/<session>/session-summary.md`
   when `docs/summaries/` is declared) is normally ruled out, with the declared copy
   named. A bible plus its chapter splits is one ruling, not two.

Below roughly six judgment calls, ask in chat (step 4). The review-page rule there is
for many *individual* rulings, not for a big file count that triage has reduced.

Name collisions to check before you propose a new kind name:

- the recipe's standard kinds (`npcs`, `summaries`, `party`, `grounding`, `prep`
  in recipe v3). A campaign kind may not shadow one;
- **`arcs`**: CampaignGenerator's `arc_triggers` reads the corpus kind named `arcs`
  and expects score-trigger tracking files in it. If the campaign already uses
  `arcs` for that, a second kind of arc document needs either the GM's
  confirmation that one kind holds both, or a different name.

### 4. Ask

- **About a dozen rulings or fewer:** ask in chat (AskUserQuestion, up to 4 per call).
- **More than that:** publish one Approve / Reject / Discuss review page (the
  `_shared/review-artifact` pattern). One card per ruling, a sticky
  undecided tally, and a Markdown export with one section per card.

Read the answers back strictly:

- **Undecided is not a verdict.** Re-ask it. Never apply your recommendation
  because the GM scrolled past.
- **A discuss note is not an approval.** State your reading and confirm it, when the
  note could produce two different files.
- **"Add" without a trust, for a new kind, is incomplete.** Ask for the trust.

### 5. Apply (only what was ruled)

1. **Adds:** edit `.mneme/corpus.yaml`.
   - A whole new directory goes under `dirs:`, which is recursive and picks up future
     files.
   - A file joining a kind that lists files goes under that kind's `files:`.
   - A new kind goes under `campaign_kinds:` **as a whole definition**: its `trust:`
     and its `dirs:`/`files:` together, at the top level of the file. Do not put
     its files under `kinds:`. `corpus check` rejects that with `unknown-kind` and
     `empty-declaration`. Shape:
     ```yaml
     campaign_kinds:
       background:
         trust: reference
         files:
         - docs/background/x-inventory.md
     ```
   - **A directory holding both source and pipeline files** (e.g. a converter's
     `chunk-*-input.txt` next to `chunk-*-response.txt` and `*-parse-error.txt`):
     declare the source files under `files:`, generated by a glob so none are
     missed, and rule out the others one file at a time. Declaring the directory
     would mine the LLM responses as well.
   - If a file is now reachable from two kinds, exactly one of them needs
     `mined_as: true`. `corpus check` says so.
2. **Outs:** append to `.mneme/corpus.rulings.yaml`, with today's date and the GM's reason.
   - Prefer one subtree entry (trailing `/`) per family over hundreds of file
     entries. A subtree out-ruling also covers future files there, which is right for
     pipeline directories.
   - **Before ruling out a subtree, check that nothing declared lives inside it:**
     `grep -n "<subtree>" .mneme/corpus.yaml`. If something does, rule out its
     siblings instead. The scanner reports a CONFLICT otherwise.
   - Put the GM's ruling in the reason (`"GM ruling 6: pipeline/process output"`), so
     the file explains itself later.
   - For more than a handful of entries, generate the file with a short script from
     the agreed list rather than by hand.
3. Validate and rebuild, all with `--dir`:
   ```bash
   mneme corpus check   <campaign> --dir <campaign-dir>   # must say valid
   mneme mp render      <campaign> --dir <campaign-dir>   # mempalace.yaml, TOC, config face
   git diff config/config.yaml                            # new authoritative kinds -> canon_wings; reference -> index_wings
   mneme mp refresh     <campaign> --dir <campaign-dir>   # mines the new files (embedder must be up)
   mneme mp status      <campaign> --dir <campaign-dir>   # want: corpus conformant, index built
   mneme mp backup      <campaign> --dir <campaign-dir>
   ```
4. **If `mp status` reports `UNDECLARED-DRAWERS`** after the refresh: the palace
   still holds drawers for files the corpus no longer declares. Usually that means
   files were renamed or removed (toee: 42 renamed `docs/summaries/` files, 2,449
   drawers, so every summary came back twice in search). `refresh` never deletes, so
   this was there before your change. Name it and ask the GM. Deleting drawers is the
   GM's call, even though no file on disk is touched. On a yes:
   ```bash
   mneme mp prune <campaign> --dir <campaign-dir>                          # preview: the list and the count
   mneme mp prune <campaign> --dir <campaign-dir> --confirm --expect <N>   # N from the preview; backs up first
   ```
   Then re-run `mp status` and take a backup.
5. Spot-check that a newly added file is searchable:
   `mneme mp search <campaign> --dir <campaign-dir> -- "<phrase from it>"`.
   Check one file from each new kind.
6. Re-run the scanner. The ruled files are gone, and only deferred ones remain.

### 6. Report and commit

Report: candidates found per signal, rulings by type (add / new kind / out / defer),
any still undecided, stale rulings and conflicts, and the final `mp status`.

Commit `.mneme/corpus.yaml`, `.mneme/corpus.rulings.yaml` and the re-rendered
`config/config.yaml` and root `mempalace.yaml` together, on a branch. (They are
replicas, but they're tracked, and they must match the corpus they were rendered
from.) One campaign per commit. Commit only when
the user asks.

## Hard rules

- The scanner is read-only. All writes are the GM's rulings, applied by you after
  explicit answers.
- Never hand-edit a mneme replica (TOC snapshot, root `mempalace.yaml`, the config
  `mempalace:` block). Change `corpus.yaml` and render.
- Never run `mempalace init` or `mempalace mine` on a mneme-managed campaign.
  `mp refresh` is the mining path.
- Never choose trust, or rule a file out, on the GM's behalf. That includes "obvious"
  pipeline output: recommend it, then let the GM rule.
- One campaign per run and per commit.
