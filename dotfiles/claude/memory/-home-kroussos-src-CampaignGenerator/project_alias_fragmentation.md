CampaignGenerator has **no single authority for campaign-entity alias→canonical mapping or entity declaration**. The same fact ("these surface forms denote one entity") is hand-entered in 4+ stores with 4 schemas, and drift between any two is a fragmentation bug. Surfaced while building merged entities in the ensemble path.

**The concrete failure (`facts_to_state.load_bundles`):** an entity survives as one merged bundle only if `is_known = _norm_subject(aliases.get(raw, raw)) in known_names`. But `aliases` comes from `aliases.json` (hand-authored) while `known_names` comes from inventory `.md` + `.dedup_state.json` (different hand-curated files). If a canonical is in one store but not the other, the entity flips to *anonymous* → re-keyed `(type, norm, chapter_location)` → the same NPC fragments into one dossier per location, or is dropped under `--known-only`.

**Two facets, both fragmented:**
- Facet 1 — variant→canonical *mapping*: dossier frontmatter `aliases:` (`docs/npcs/*.md`, `{canonical:[aliases]}`, written by `planning.write_dossier`, read by `campaignlib.npc.load_alias_map`); `aliases.json` (`{canonical:[variants]}`, hand-authored, read by `synthesise_world_state`/`facts_to_state`/`synthesise_polish`/`synthesise_facts`); `.alias_decisions.json` (rename/subset/overlap decisions, written by ensemble-alias-review skill, read by ensemble-alias-merge skill).
- Facet 2 — entity *declaration* (which proper nouns are real entities): module inventory `.md` bold spans; `.dedup_state.json` `clusters_confirmed[].{canonical,aliases_recorded}`; filename-stems (`harbin_wester.md`→harbin,wester via `_stem_words`). All read by `facts_to_state.load_known_names`. `load_bundles` needs BOTH facets at once, from disjoint files that must agree.

**Key structural finding:** every store is *independently hand-curated — none is generated from another*. Sharpest instance: `.alias_decisions.json` lives entirely in skill-land; no Python reads/writes it, so the pipeline's own alias decisions are invisible to the pipeline's dedup. `.dedup_state.json` also has **no in-repo (CampaignGenerator) writer** — it is emitted by the **`dossier-merge` Claude Code skill** in a *different repo* (`~/src/mytools/dotfiles/claude/skills/dossier-merge/SKILL.md`), which is why every grep inside CG found nothing. That skill backs up the dossier dir, heuristically clusters duplicate dossiers (alias-hint → compound-filename → substring → title-prefix-strip → Levenshtein≤2), and records the human's ratified merge decisions as `clusters_confirmed[].{files,canonical,aliases_recorded}` / `clusters_rejected[]` / `clusters_deferred[]` for resumable runs. Because `clusters_confirmed` captures **both** facets at once (canonical declaration *and* variant→canonical mapping) as a byproduct of a human-in-the-loop session, and `facts_to_state.load_known_names` *reads* it, the `dossier-merge` skill is the strongest existing **candidate seat for the single authority** — the one place a human already ratifies both facets together. Today it is still just one of the four siloed stores (per-session decisions, not a maintained registry), and the producer→consumer edge crosses a repo boundary (`mytools` skill → CG Python).

**Scope boundary:** `kanka_push`/`kanka_sync` "canonical" = external-Kanka entity identity; `fivetools_catalog`/`fivetools_ingest` "canonical" = published 5etools reference names. Different bounded contexts — NOT copies of the campaign registry. Kanka is a legitimate *consumer* (reference registry at its push boundary); fivetools is out of scope.

**Why:** because the stores are siloed hand-curated copies (not a lossy DAG), the fix direction is **one human-curated entity registry → generated projections** for each consumer shape, replacing the 4 copies — not reconciling them. This is a scope/attribution precision decision (single authority), so it needs a human design pass before implementation.

**How to apply:** when touching alias/canonical handling in the ensemble→state path (`facts_to_state`, `synthesise_world_state`, `synthesise_facts`, `ensemble_merge`) or the dossier path (`planning`, `campaignlib.npc`, `distill`, `campaign_state`, `party`, `vtt_summary`, `sd_narrate`), remember these two families don't share a store and their schemas differ. Filed as **CampaignGenerator#129** (sibling to #128 transient-vs-canon taxonomy); design anchor, not ready-to-code — the fix is a scope/attribution precision decision needing a human design pass.

**Supply-side sibling — CampaignGenerator#130 (name provenance):** the entity-declaration inventory (facet 2) has **three provenances but one curation path**. Names come from (1) the canonical adventure module, (2) supplemental material in `refs.yaml`, (3) on-the-fly generated content. Only (1) has a path into the authored inventory (GM hand-compiles `module_inventory.md` → `load_known_names`). refs.yaml supplements reach only the *retrieval* axis — `fivetools_catalog` (its docstring: "knows where things are, not what they say") **and** the live 5etools MCP runtime tree built by `launch_5etools_mcp.py` (`refs-index.json` + `_build_homebrew`) — never `known_names`. On-the-fly names only back-feed incidentally via `.dedup_state.json`. One-liner: **retrievable but not declared** → those names miss the inventory and fragment in `load_bundles`. Fix ≠ bulk-join catalog into `known_names` (kills the allowlist discriminator; violates the scope-decision→human-checkpoint rule). Fix = a *proposal path per source* ending in GM selection (candidate proper nouns → GM picks → authored inventory), mirroring `dossier_proposer.py`; the natural hook is `launch_5etools_mcp.py`'s `refs-index.json`. #129's "generated projections" applies to the *mapping* facet only — *declaration* from a supplement needs human selection, not projection. Trilogy: #128 file persistence, #129 identity mapping, #130 identity provenance.
