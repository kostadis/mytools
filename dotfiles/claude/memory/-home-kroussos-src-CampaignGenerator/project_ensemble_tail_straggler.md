`ensemble_extract.py`'s `--endpoints` dispatch is one worker thread per endpoint pulling from a shared queue (work-stealing). **Mid-queue this self-balances** — if one Spark stalls, the other keeps pulling units. **The tail is the hole:** once the queue drains, each worker holds its last unit; a free worker calls `queue.get()`, gets nothing, and EXITS even while another endpoint is still wedged on a unit. So the run always waits for the slowest endpoint at the very end, with no one able to steal its work.

**Observed (2026-05-30, chapter_52 of the ch50–55 run):** 11/15 units finished in ~7 min; the last 4 (temporal.s3 + interiority.s1/s2/s3) hung ~1h44m, then completed within ~2 min of each other. Root cause was NOT a Spark fault — the user was running work on spark1 directly (07:48→10:30), starving its vLLM serving; the trailing units pinned to that endpoint just waited. The openai-retry fix ([[project-local-extraction-pipeline]]) is why it recovered instead of dying.

**Fix the user designed — speculative re-execution (straggler mitigation, à la Spark/MapReduce), NOT a fixed timeout.** A kill-and-fail timeout would discard work that was only *paused*; and the trigger shouldn't be a magic constant. Instead: when a worker finds the queue empty, check if any unit is still in-flight on another endpoint and **re-dispatch the longest-running one on itself**, taking whichever copy finishes first (dedup by the `(pass, sample)` key, which already exists). Trigger is "a free fast endpoint exists while a unit is still running" — exactly the condition observed. Add a `min_age` guard (~60s) so freshly-started units aren't needlessly duplicated. Bounded waste (only tail units), self-correcting under contention.

**IMPLEMENTED 2026-05-30 (PR #70, branch feat/ensemble-speculative).** Default ON with 2+ endpoints; `--no-speculative` restores the old wait-it-out behaviour (still the safer choice for ATTENDED runs where the user may grab a Spark mid-job). `run_unit` switched `subprocess.run`→`Popen` + `register_proc`/`is_cancelled` so a losing copy is terminated; pure tested `pick_straggler()` picks the oldest in-flight unit past `--spec-min-age` (default 60s) under `MAX_COPIES=2`; winner settles `results[name#k]`, kills the loser, so `join()` returns instead of blocking on the slow box. Single-endpoint runs byte-for-byte unchanged. Tests: `tests/test_ensemble_dispatch.py`.

**SPECULATION ALONE IS INSUFFICIENT — the real floor is a per-unit timeout (commit 66ecd8f, 2026-05-31).** First full 56-chapter run hung ~6.5h on chapter_03. **CORRECTED root cause: the laptop slept mid-run** (confirmed: it sleeps — a second ~3.8h gap between ch06 and ch07 the same morning was also sleep). Sleep froze the Python procs with their TCP sockets to vLLM open mid-read; on wake the sockets were stale/half-open (peer gone for hours, no keepalive) and a blocked `read()` on a half-open TCP connection NEVER returns — hence `do_sys_poll` forever. My initial "vLLM degraded / runaway decode toward the 16000 `max_tokens` ceiling" diagnosis was UNSUPPORTED inference — never observed; live metrics showed 0 preemptions and ~0% KV cache, and the sleep fact explains it without any server degradation. Speculation could not help (re-dispatches onto a FREE endpoint; neither was free). The old `split_run.sh` had `timeout 600` per pass; `ensemble_extract.py` had dropped it — the regression. Fix: `--unit-timeout` (default 600s) → `communicate(timeout=)` kills the subprocess, `run_unit` returns `timed_out=True`, dispatcher re-queues up to `--unit-retries` (default 3) then fails the run; `next_task` merges a re-queued key into any still-running sibling copy. `--unit-timeout 0` = unbounded. Lesson: a frozen/stale socket is neither a "slow box you wait out" nor an "error you retry" — only a wall-clock cap bounds it. Diagnosis tell: procs in `do_sys_poll` + empty per-unit cache dirs + a wall-clock gap with no log activity = host sleep, not model degradation. OPEN REFINEMENT: the OpenAI client in `campaignlib.make_client` is built with NO timeout, so a dead socket blocks until the 600s unit cap; adding an HTTP request/read timeout would catch a stale socket in seconds. Monitoring gap: per-chapter logs are block-buffered (no `PYTHONUNBUFFERED`) so within-chapter `[start]/[retry]/[done]` don't flush live — use the master `run.log` + `merged.json` counts.

**Original priority note (why it was deferred):** only worth it for UNATTENDED headless batch runs (e.g. all 55 chapters). The old `split_run.sh` had `timeout 600` per pass; `ensemble_extract.py` had dropped it.
